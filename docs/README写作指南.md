# README 写作指南

> README 是别人打开你仓库后看到的**第一个文件**，相当于项目的门面。
> 本文讲清楚：为什么写、写什么、怎么写，并附 Markdown 语法速查与发布前自查清单。

## 1. 为什么 README 重要

- **30 秒法则**：陌生人打开仓库，30 秒内决定是继续看还是关掉；
- **降低使用门槛**：安装、运行、示例写清楚，别人才能跑起来；
- **展示专业度**：结构清晰、命令可复制的 README，比"代码能跑"更能体现工程能力；
- **对未来自己友好**：三个月后你也会忘记项目怎么启动。

README 不是"项目说明书"，而是**给读者的入口**：先告诉他能得到什么，再告诉他怎么做。

## 2. 一个好 README 的骨架

按重要程度排序，可以按项目规模删减：

```text
1. 标题 + 一句话定位
2. 徽章（可选）
3. 项目简介：解决什么问题、给谁用
4. 功能 / 内容列表
5. 目录结构
6. 安装 / 环境要求
7. 快速开始（最小可运行示例）
8. 使用示例 / 截图
9. 文档索引（指向 docs/）
10. 贡献方式
11. 许可证
12. 更新日志（可选）
```

### 2.1 标题与一句话定位

标题就是仓库名；紧接着用一句引用或加粗句子说明"这是什么"。

```markdown
# Learning · 编程学习仓库

> 记录 Python 课程实验代码、学习笔记，以及从零开始实践 Git / GitHub 的过程。
```

反面例子：

```markdown
# learning
```

只有一个标题，读者不知道里面有什么、给谁看。

### 2.2 徽章

徽章用 [shields.io](https://shields.io/) 生成，本质是一张图片：

```markdown
![Python](https://img.shields.io/badge/Python-3.9%2B-3776AB?style=flat-square&logo=python&logoColor=white)
![Git](https://img.shields.io/badge/Git-2.x-F05032?style=flat-square&logo=git&logoColor=white)
```

规则：

- 只放**有信息量**的徽章（语言、版本、构建状态、许可证）；
- 3–5 个足够，太多会显得杂乱；
- 静态徽章用 `badge/标签-内容-颜色`；动态徽章用 GitHub Actions / Codecov 等提供的地址；
- 徽章里的空格用 `%20` 或 `_`，连字符用 `--`。

### 2.3 项目简介

回答三个问题：

1. 这个项目是做什么的？
2. 为什么做它（动机 / 场景）？
3. 谁能用、需要什么基础？

```markdown
## 📖 项目简介

这是一个用于学习和练习的公开仓库，主要包含三类内容：

- Python 基础练习：课程实验中的脚本与常用数据结构速查笔记；
- Git / GitHub 实践：分支、提交、推送、合并的完整操作演示；
- 写作与工程习惯：README 怎么写、提交信息怎么规范。
```

### 2.4 目录结构

用树形图，注释写清楚每个目录的用途：

````markdown
```text
learning/
├── README.md
├── docs/               # 学习文档
└── python-basics/      # Python 练习
    ├── notes/          # 笔记
    └── practice/       # 代码片段
```
````

目录很多时不必全列，只列**读者需要关心的部分**。

### 2.5 安装与快速开始

这是 README 最容易被跳过、也最不该省略的部分。要求：

- 给出**完整可复制**的命令；
- 写清楚**前置条件**（Python / Node 版本、依赖）；
- 给出一个**最小可运行示例**；
- 说明预期输出。

````markdown
## 🚀 快速开始

需要 Python 3.9 及以上版本。

```bash
git clone https://github.com/Hub-Jihoo/learning.git
cd learning
python python-basics/实验1.py
```
````

注意：

- Windows / macOS / Linux 命令不同时，分别列出；
- 不要假设读者已经装了依赖；
- 命令放在代码块里，不要用截图。

### 2.6 文档与链接

README 保持"总览"定位，细节放 `docs/`：

```markdown
| 文档 | 内容 |
| --- | --- |
| [Git 与 GitHub 操作指南](docs/Git与GitHub操作指南.md) | 克隆、分支、提交、推送、合并 |
| [README 写作指南](docs/README写作指南.md) | 本文 |
```

链接使用**相对路径**，仓库改名或换域名后仍然有效。

### 2.7 贡献与许可证

个人项目可以简单写：

```markdown
## 🤝 贡献

欢迎通过 Issues 指出错误或提出建议。
```

许可证不是可选项：**没有 LICENSE 文件 = 默认保留所有权利**，别人不能合法复用。
常用选择：

- MIT：最宽松，允许商用、修改、再分发；
- Apache-2.0：宽松 + 专利授权；
- GPL-3.0：衍生作品必须同样开源。

在仓库根目录添加 `LICENSE` 文件即可，GitHub 会自动识别并显示在仓库页面上。

## 3. Markdown 语法速查

README 使用 GitHub Flavored Markdown（GFM）。

### 3.1 标题与强调

```markdown
# 一级标题（README 中通常只用一次）
## 二级标题
### 三级标题

**加粗**
*斜体*
~~删除线~~
`行内代码`
```

### 3.2 列表与任务列表

```markdown
- 无序列表
  - 嵌套项

1. 有序列表
2. 第二项

- [x] 已完成
- [ ] 待完成
```

### 3.3 链接与图片

```markdown
[链接文字](https://example.com)
[相对链接](docs/README写作指南.md)
[锚点跳转](#快速开始)

![图片描述](images/demo.png)
```

图片建议放在 `docs/images/` 或 `assets/` 目录，避免根目录杂乱。

### 3.4 代码块

````markdown
```python
print("hello")
```

```bash
git status
```
````

代码块标注语言可以获得语法高亮。行内命令用反引号：`git commit -m "..."`。

### 3.5 表格

```markdown
| 命令 | 作用 |
| --- | --- |
| `git add` | 暂存改动 |
| `git commit` | 提交快照 |
```

表格适合做命令速查、参数说明、文件清单。

### 3.6 引用、分割线与折叠

```markdown
> 提示或注意事项

---

<details>
<summary>点击展开更多</summary>

这里是被折叠的内容。

</details>
```

`<details>` 适合放长日志、安装细节，避免 README 过长。

### 3.7 锚点

GitHub 会为标题自动生成锚点：中文标题也能跳转，空格变成连字符。

```markdown
[跳到快速开始](#快速开始)
```

标题重复时，锚点会自动加 `-1`、`-2` 后缀。

## 4. 写作原则

### 4.1 面向读者，而不是面向自己

写给"第一次打开仓库的人"，不是写给"已经知道答案的自己"。

- 不说"很简单，直接跑就行"；
- 不省略前置步骤；
- 不假设读者知道你的目录习惯。

### 4.2 先结论，后细节

第一段告诉读者"这是什么、能干什么"，再展开安装和原理。

### 4.3 命令可复制

所有命令放进代码块，避免把提示符 `$` 也复制进去（或者明确说明 `$` 不是命令的一部分）。

### 4.4 保持更新

README 是活的文档。改接口、改目录、改依赖时，同步更新 README。
过时的 README 比没有 README 更误导人。

### 4.5 中英文排版

- 中文与英文、数字之间加空格：`使用 Python 3.9 运行`；
- 代码、命令、文件名用反引号包裹；
- 专有名词保持原样：Git、GitHub、Markdown、Python。

### 4.6 控制长度

- 根 README 建议控制在 100–300 行；
- 细节放 `docs/`，README 只留入口；
- 用表格和列表代替大段文字。

## 5. 反例与正例

| 反例 | 问题 | 正例 |
| --- | --- | --- |
| `# project` | 没有说明 | `# Learning · 编程学习仓库` + 一句话定位 |
| `pip install -r requirements.txt` 无任何上下文 | 读者不知道要在哪个目录、什么 Python 版本 | 先写环境要求，再给完整命令 |
| 一大段文字描述代码逻辑 | 难以扫读 | 用列表 / 表格分点 |
| 截图代替命令 | 无法复制、无法搜索 | 代码块 |
| 只写"运行 main.py" | 缺依赖、缺参数 | 给出完整命令与示例输入输出 |
| 提交了个人邮箱、学号 | 隐私泄露 | 使用匿名邮箱，敏感文件不公开 |

## 6. 本仓库 README 的拆解

以根目录 [`README.md`](../README.md) 为例：

| 部分 | 作用 |
| --- | --- |
| 标题 + 引用 | 一句话说明仓库定位 |
| 徽章 | 标明语言、工具、状态 |
| 项目简介 | 三类内容 + 隐私声明 |
| 目录结构 | 让读者快速建立空间感 |
| 内容索引 | 表格指向具体文件 |
| 快速开始 | 克隆、运行、阅读顺序 |
| 学习进度 | 用任务列表展示状态 |
| 隐私说明 | 公开仓库的必查项 |
| 更新日志 | 记录每次变更 |
| 贡献 / 许可 | 告诉别人如何参与、能否复用 |

写作思路：**读者先看"这是什么" → 再看"有什么" → 最后看"怎么用"**。
所以把简介和目录放前面，把细节和命令放后面。

## 7. 发布前自查清单

- [ ] 标题和一句话简介能让人 10 秒内知道项目是什么
- [ ] 有目录结构说明
- [ ] 安装 / 运行命令完整、可复制、有版本要求
- [ ] 有一个最小可运行示例和预期输出
- [ ] 文档链接使用相对路径且能打开
- [ ] 没有学号、真实姓名、手机号、私人邮箱、token
- [ ] 没有提交 `.idea/`、`.vscode/`、`__pycache__/` 等本地文件
- [ ] 图片有描述文字，路径正确
- [ ] 表格、代码块渲染正常（在 GitHub 网页上预览一遍）
- [ ] 已决定是否添加 LICENSE
- [ ] 更新日志或最近提交信息能说明本次变更
